# ponytail

Pull the code back and tie it off: same face, less hanging in it.

A ponytail pass leaves the program indistinguishable from the outside and smaller and
plainer on the inside. If anyone can tell from the outside that it ran, it was not a
ponytail pass — it was a behaviour change wearing one, and it goes back.

## The one rule

**Behaviour is identical, and you prove it rather than believing it.**

In this repository the proof is unusually cheap, so there is no excuse for skipping it:
`examples/` holds generated output for every format the tool produces — console, JSON,
SARIF, HTML, and the statements. Regenerate it. One changed byte means the pass changed
behaviour. Either that byte is an improvement you can name and defend in the changelog, in
which case it belongs in its own commit as a change, or the pass is wrong.

**It is not a performance change, and it does not claim to be one.** Compaction removes
duplicated *places*, not work: folding three copies of a calculation into one leaves the
same calculation. Do not describe a pass as making anything faster, and do not reach for
one when something is slow — that is a separate job, with a measurement before and after.
The line count is not the metric either: a pass that adds shared code with the comments to
explain it can leave the tree bigger and still be the right change.

## What it changes

1. **Duplication that is one idea written twice.** Two functions doing the same work in two
   idioms become one with the difference as a parameter — but only when it really is one
   idea. Two things that merely look alike today and drift apart tomorrow are not.
2. **Parallel implementations of one model.** Four renderers that each re-derive grouping,
   ordering and severity from raw findings should derive it once and present it four ways.
3. **Indirection with one caller.** A wrapper, a re-export, an options object, or a helper
   used in exactly one place, where inlining it makes the call site shorter *and* clearer.
   If inlining makes the call site longer, the indirection was earning its keep.
4. **Dead and speculative surface.** Unused exports, options nothing passes, branches
   nothing reaches, type parameters with one instantiation, defensive checks the type system
   already makes impossible.
5. **Shapes fighting the language.** Manual loops that are a `map`/`filter`/`flatMap`, hand
   rolled lookups that are a `Map`, long `if`/`else` chains over a closed set that are a
   record, argument lists past three or four that want an object.
6. **Types that restate each other.** A hand-written interface that is `Pick`, `Omit` or a
   return type of something that already exists.
7. **Tests that repeat their setup.** A table-driven test in place of eight near-identical
   ones — but only where the failure message stays as specific about what broke.

## What it never touches

- **Doc comments and the reasoning in them.** The comments here explain why refusals exist:
  why a skipped rule never becomes a pass, why the browser runner places results by
  position, why the language matrix is sparse. That prose is the most valuable text in the
  repository. Compaction deletes code, never reasons. If a comment describes code you
  folded, rewrite the comment to describe the new code — do not drop it.
- **Names.** No shortening identifiers, no single letters, no abbreviating `completeness` to
  `comp`. Compact means fewer moving parts, not fewer characters.
- **Line-level cleverness.** No chaining six operations into one unreadable expression, no
  nested ternaries, no clever bit tricks, no removing intermediate variables that name a
  thing worth naming. Fewer lines is a side effect of the pass, not its target.
- **Public API.** Exports in `package.json`, CLI flags, config keys, the JSON and baseline
  schemas, SARIF field names. Any change there is a release decision with a changelog entry
  and possibly a schema version, so it is not a ponytail change.
- **`src/statement/templates/`.** Those files are near-parallel on purpose — each is a
  document under its own country's law, not a translation of another's. Factoring their
  shared sentences out re-introduces exactly the coupling that was deliberately removed.
- **Generated and vendored files.** `examples/`, `dist/`, `pnpm-lock.yaml`, fixtures. The
  examples are regenerated by their script, never edited.
- **Behaviour, in any amount.** A bug you find during a pass gets written down and fixed in
  its own commit, before or after, never inside it.

## How to run a pass

1. **Pick one module and say so.** `src/audit/report/`, or `src/cli/`, or one file. A pass
   that spans the tree cannot be reviewed and cannot be bisected.
2. **Read it whole before changing anything**, including its tests. Most apparent duplication
   in this codebase is two cases that differ in one condition that matters; the comments
   usually say which.
3. **Record the starting point**: `find src -name '*.ts' | xargs wc -l | tail -1`, and the
   file sizes in the area you are about to touch.
4. **Make the moves above, one kind at a time**, checking after each that the suite still
   passes. Ten small verified steps beat one large plausible one.
5. **Run the gates.** All of them, in this order, all green:

   ```bash
   pnpm lint
   pnpm typecheck
   pnpm test
   pnpm build && pnpm smoke
   pnpm examples && git diff --exit-code examples/   # the real proof
   ```

   `git diff --exit-code examples/` is the one that matters. If it is not clean, stop and
   explain the diff before doing anything else.
6. **Re-read your own diff as a reviewer.** For every deletion: what did that line do, who
   relied on it, and what now does it instead? For every merge: name the case that would
   make the two callers need to diverge again, and say why it will not happen.
7. **Commit alone**, with a message that reports the numbers rather than adjectives:

   ```
   refactor(report): one model behind the four report formats

   Console, HTML, JSON and SARIF each re-derived grouping, ordering and
   severity from raw findings. They now share it. 1,536 lines to 1,120;
   examples/ regenerated byte-identical.
   ```

   `refactor(<area>):` is the type. No behaviour change means no `CHANGELOG.md` entry —
   except the line-count ledger the roadmap asks each release to carry.

## On new code, before the PR

Run a pass over your own branch before opening it: the diff is small, you still remember why
every line is there, and the duplication you are about to introduce is easier to see against
what you just read than against a module six months old. The one addition to the rules: at
this stage, code you wrote this session that is *not yet used by anything* is dead surface —
delete it rather than leaving it for a future caller.

## When not to use it

- On a branch that is fixing a bug or adding a feature, mid-work. Finish the change, get it
  correct, then compact.
- On code you do not understand yet. Compaction is a judgement about which differences
  matter; without the judgement it is just deletion.
- When the gates cannot run — no build, no browser for the browser-mode tests, a broken
  suite. Without proof there is no pass.
- When the honest answer is that the duplication is load-bearing. Two implementations that
  must be able to diverge stay two implementations, and a comment saying so is the right
  output of a pass that decided to leave something alone.
